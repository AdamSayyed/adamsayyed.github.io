WairPlay – Cross-Platform P2P File Transfer

WebRTC, Socket.IO, Node.js, Manifest V3 Chrome Extension, JavaScript

View Project on GitHub

1. Introduction & Motivation

There's a moment every developer has. You want to send a file from your laptop to your phone—something that should take three seconds—and instead you're emailing it to yourself, wrestling with a USB cable, or opening Google Drive for a 400KB PDF.

AirDrop solves this perfectly, if everyone you care about has a Mac or iPhone. I wanted that for everything else. So I built WairPlay: a cross-platform, browser-native AirDrop clone that works over local Wi-Fi using WebRTC and a Chrome Extension.

The premise is simple: two devices on the same Wi-Fi network should be able to exchange a file in under five seconds, without touching a server, without creating an account, and without installing anything. This page breaks down the full system architecture, the three-component design, the WebRTC handshake flow, and the complex corner cases forced by Chrome Manifest V3.

2. System Architecture

The system has three distinct components with a strict separation of concerns. The most important design decision: the server is dumb by construction. It never sees file data.

  • Signaling Server: Node.js + Socket.IO on port 3000. Maintains an in-memory activeDevices array. Relays WebRTC payloads between peers. No file data, ever.
  • Web Client: Vanilla JS, no framework. Connects via Socket.IO, renders device list, owns the full WebRTC lifecycle through a WairPlayPeer wrapper class.
  • Chrome Extension: Manifest V3. Three-layer architecture: Service Worker orchestrates, Offscreen Document runs WebRTC, Popup is a lightweight UI client with zero network logic.

Two protocols: Socket.IO (over WebSocket) handles all signaling—device registration, presence, and the exchange of WebRTC offers, answers, and ICE candidates. WebRTC RTCDataChannel handles the actual bytes. Once the P2P channel is open, the server is completely out of the loop.

“The file data never touches the server. It travels at full LAN speed, DTLS-encrypted, directly between devices—the server is architecturally incapable of intercepting it.”

3. The End-to-End Transfer Lifecycle

The entire sequence progresses cleanly from discovery to direct byte transfer:

register-device → send-file-request → accept-file → SDP offer/answer → ICE candidates → DataChannel open → chunked transfer

The first three steps are pure Socket.IO user-facing permission flows before WebRTC even starts. Only after the receiver clicks “Accept” does either side attempt to construct an RTCPeerConnection.

4. WebRTC Negotiation & ICE Trickle

The sender creates the connection, opens a DataChannel named "files", and generates an SDP offer. That offer gets relayed via the signal Socket.IO event to the receiver, who processes it and returns an SDP answer. Both sides then exchange ICE candidates—the browser’s mechanism for discovering viable network paths—until a direct route is established.

// Sender side (simplified)
const pc = new RTCPeerConnection({ iceServers: STUN_SERVERS });
const dc = pc.createDataChannel("files");
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
socket.emit("signal", { to: targetId, payload: offer });

// ICE trickle
pc.onicecandidate = ({ candidate }) => {
  if (candidate) socket.emit("signal", { to: targetId, payload: candidate });
};

5. File Chunking & Backpressure Handling

Files are read via FileReader, sliced into 64KB ArrayBuffer chunks, and written to the DataChannel sequentially. The naive implementation breaks on large files—the DataChannel has a fixed internal buffer, and if you write faster than the network drains it, you’ll overflow and drop data.

The fix is backpressure handling via bufferedAmountLowThreshold. When dc.bufferedAmount exceeds a threshold, the sender pauses and waits for the bufferedamountlow event before resuming:

dc.bufferedAmountLowThreshold = 64 * 1024; // 64KB
dc.onbufferedamountlow = () => sendNextChunk();

function sendNextChunk() {
  if (dc.bufferedAmount > dc.bufferedAmountLowThreshold) return;
  const chunk = fileBuffer.slice(offset, offset + CHUNK_SIZE);
  dc.send(chunk);
  offset += CHUNK_SIZE;
  if (offset < fileBuffer.byteLength) sendNextChunk();
}

On the receiving end, WairPlayTransfer accumulates incoming ArrayBuffer chunks and matches them against previously sent JSON metadata (filename, total size, chunk count). Once all chunks arrive, it reconstructs the final Blob and triggers a download.

6. The Chrome Extension: Manifest V3 Architecture

The web client was relatively clean, but building the Chrome Extension presented major architectural hurdles. Manifest V3 prohibits several APIs in Service Workers that are fundamental to persistent WebRTC connections, forcing a decoupled three-layer design:

  • Layer 1: The Service Worker (background.js): Ephemeral by nature; it can spin down at any moment. Its two jobs: ensure the Offscreen Document exists on startup, and surface chrome.notifications when an incoming file request arrives. It also acts as a chrome.storage proxy, since Offscreen Documents lack direct access to that API.
  • Layer 2: The Offscreen Document (offscreen.js): This is where all actual networking lives. The Offscreen Document API provides a persistent hidden DOM context—the only place in MV3 where you can maintain a long-lived WebSocket connection and construct an RTCPeerConnection. It owns the Socket.IO connection, the WebRTC handshake, and triggers the chrome.downloads call that saves received files. Reading saved server URLs requires round-trip messaging through the background proxy.
  • Layer 3: The Popup (popup.js): Intentionally designed as a dumb UI shell with zero network logic. It polls the Offscreen Document for state via chrome.runtime.sendMessage and renders whatever state it receives.

7. Solving the IPC Memory Problem

The hardest engineering constraint emerged during sending: when a user picks a file in the popup, that file must be transferred to the Offscreen Document. The naive approach—serializing it as an ArrayBuffer through sendMessage—immediately crashes the IPC port on anything larger than a few megabytes because Chrome stringifies messaging payloads.

The solution was to keep the file in popup memory as a Blob and pass a lightweight URL reference string instead:

// popup.js — don't serialize the file, just reference it
const blobUrl = URL.createObjectURL(file); // "blob:chrome-extension://..."
chrome.runtime.sendMessage({ type: "send-file", url: blobUrl, meta: fileMeta });

// offscreen.js — fetch it natively, no IPC memory pressure
const response = await fetch(blobUrl);
const buffer = await response.arrayBuffer();
// slice and send via transfer.js

The Blob URL keeps actual file bytes localized in popup memory. The Offscreen Document fetches it natively as if it were any other resource. Chrome handles cross-context memory access internally, preventing IPC serialization crashes.

8. MV3 Architectural Summary

Manifest V3 Constraint WairPlay Workaround Solution
No WebRTC in Service Workers Offscreen Document owns all RTCPeerConnection logic
No persistent WebSocket in SW Socket.IO connection lives exclusively inside the Offscreen Document
No chrome.storage in Offscreen Background SW acts as a storage proxy via asynchronous IPC messaging
IPC crashes on large binary buffers Pass lightweight blob: URL strings; Offscreen fetches bytes natively

9. Limitations & Future Roadmap

While fully functional on local networks, current known trade-offs include:

  • STUN-only ICE: Works reliably on flat home LANs, but fails across subnets or strict symmetric NATs without a fallback TURN relay server.
  • In-Memory Signaling: Active device presence is volatile; server restarts require re-registration.
  • Resumability: Mid-transfer WebRTC dropouts currently restart from scratch. Adding sequence-numbered chunks with a resume handshake would bolster large transfer reliability.
